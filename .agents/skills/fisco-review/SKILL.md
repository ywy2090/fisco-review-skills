# Review FISCO-BCOS code (reviewer side)

Reviews in this repo (see the #5544/#5547 engine-split history) are **round-based, severity-scored, and claim-audited**. The reviewer first checks whether the PR description honestly describes the diff, then correctness on the *live production path*, then structure and scope. Findings carry severity + scope + location + code evidence and an actionable fix. Each round re-checks prior findings at the new head before adding new ones, with a stated convergence rule.

## Review modes

Two axes are easy to conflate: a **round** is a numbered pass in the PR's review history (Round 1, Round 2, …), while **delta vs full** is how this round is executed. Most rounds run delta; full is for a first deep pass or an explicit request.

- **Delta (default)** — for a round re-check or when the head barely changed since the last review: verify each prior finding at the new head (fixed / partial / rejected-with-reasoning), run checklist spot-checks, write the round report. Main-thread only, no sub-agents. Cost: tens of k tokens, minutes.
  A round where the head is **unchanged** and only author replies arrived is pure claim-verification: check each "Fixed in <sha>" against the recorded fix diff, and each **rejection** against its stated technical premise — a rejection has no diff to check, so the code line or tooling semantics the rejection rests on must be re-verified at the head, and a premise that no longer holds reopens the finding. No file re-reads beyond those diffs and premises.
- **Full** — when the user asks ("full"/"全量") or for the first review of a PR spanning **>2000 changed lines across >5 modules**: parallel sub-agents per module under the delegation contract in [references/checklist.md](references/checklist.md), then an aggregation gate. Cost: several M tokens; use deliberately. Below that threshold the **main thread reads the whole diff directly** (the "single-pass" path) — parallel sub-agents do not pay for themselves on mid-size PRs: they slice files and cut the cross-file symmetry the reviewer needs, and this skill's own #5549 runs measured 2.4–5.6M tokens per agent (3–5× the budget) with *lower* recall than one human pass over the same head. Delta findings are not re-derived in full mode unless the head changed.

## Workflow

0. **Announce the start.** Print the start marker first, before any analysis: `准备开始 review PR #<number>`, then the PR identity — title, `base → head @ short-sha`, and `+n/-m` diffstat. The user uses this to confirm the right PR and commit are under review.

1. **Pin the fixed point and confirm the commit.** Branch/PR/base as given, e.g. `git diff <base>...HEAD` (three-dot). Record the commit list, per-commit subjects, and diffstat (+/- and file list) — these frame the review. **Confirm the base too**: use the PR's `base.sha` (fetched with `head.sha`) as the three-dot base — a local `release-3.18.0`/`master` ref can be stale and turn a 46-file PR into a 1500-file diff; base drift invalidates the diffstat and file list exactly like head drift below. **Confirm the PR commit is the right one before reading further**: fetch the PR's stated head (`head.sha`) from the tracker and verify that sha exists locally (`git rev-parse <sha>^{commit}`). The head ref usually lives on the author's fork and is **not** a local ref — do not `git rev-parse <ref>` against local branches. If the sha is not yet local, fetch it first (`git fetch <fork-remote> <branch>` or `git fetch <remote> pull/<n>/head:refs/pr/<n>`), then re-verify. If the tracker head differs from the sha the review was named for, the branch has moved — re-target first. **Head drift is the review's own bug**: a review's conclusions are only valid for the head it read, and the head can advance between "I fetched it" and "I wrote the report". Re-fetch the tracker head immediately before writing the report; if it moved, the new commits are unreviewed surface — say so in the verification boundary rather than implying they were covered. Unreviewed surface is a **convergence blocker**, not a note: commits absorbed into the ledger from a parallel author session (or head drift) must each be audited — diff read, checklist spot-checks, affected-target verification — before the round report may state convergence (see the fast path). A blocker landed in absorbed-and-unaudited commits is a review miss, not an author error: the skill saw the drift and skipped the audit. This is why a reviewer who "reviewed yesterday" can miss a blocker that landed this morning. **Stacked PRs** (this repo's engine-split stack): the review target is the PR's *own* commits (head minus the stack it depends on); stack commits inherit the base PR's findings ledger and are only re-verified, never re-reviewed. Compute the boundary from the commit list — the PR's own commits are those it introduces beyond the branch it stacks on (e.g. `git log <stack-base>..<head>`) — not the three-dot diffstat.
2. **Acquire the review lock, then materialize into a per-review directory.** Check `git worktree list` and the current branch, and compute the directory `.agents/reviews/pr-<number>-<head-short-sha>/` (head sha from step 1). **Acquire a file lock on it** so concurrent reviews of the same PR@sha don't clash: run `scripts/lock.sh acquire <dir>` — it does the atomic `mkdir <dir>/.lock` + PID/timestamp, polls every 2 s up to a 30 s timeout, and breaks a stale lock (30 min TTL) whose PID is dead. On failure, surface `review PR #<number>@<sha> 已在进行中`. Release at the finish marker with `scripts/lock.sh release <dir>`; wrap the review so an error exit also releases it.
   Then materialize: if the reviewed branch is not the checked-out branch (common: this repo's checkout may sit on an unrelated feature worktree), extract the head tree once and review only those blobs:
   `git archive <head-ref> <dirs> | tar -x -C .agents/reviews/pr-<number>-<head-short-sha>/tree`
   `<dirs>` = the diffed modules **plus headers-only of the modules they include — directly, or any transitive header a cross-module question needs** (e.g. `bcos-protocol` protocol headers, txpool/evm interfaces) so cross-module questions resolve in-session instead of dying as "could not determine". Immediately **verify the tree against head**: run `scripts/verify_tree.sh <head-ref> <tree-dir>` and fail fast on any mismatch — a stale tree silently invalidates every line number in the report. Route every other intermediate artifact into this directory (fetched PR record, findings ledger, known-items list, aggregated findings). Keep it untracked — do not commit review intermediates. Never read working-tree files when reviewing another branch — line numbers and content must all refer to the materialized head tree.
3. **Fetch the review record and spec claims.** The PR description is the spec — quote its claims verbatim and treat "no cutover", "refactor/extraction only", "no behaviour change" as **audit assertions to verify, not facts**. Also pull: prior review rounds and author replies (`Fixed in <sha> — …` inline, with the per-finding evidence in the round summary reply; `Not changed — …`), issue comments, codecov patch coverage, and issue numbers (#NNNN) or upstream-parity references (op-geth) cited in code and comments. Prefer this skill's `scripts/fetch_pr.py <number> <review-dir>` — one run saves the full record (pr/commits/reviews/comments/issue-comments/codecov) and prints the pin summary (head/base/commits/diffstat/rounds) for the start marker; ad-hoc curl is the fallback, not the default.
4. **Verify the claims first.** Classify the PR: pure refactor / behaviour change / mixed. Grep the production wiring — does `EngineServiceInitializer` (or the analogous root) still construct the legacy service? Does anything new have a **live production caller**, or is it only referenced by its own tests? Findings on live paths outrank findings on not-yet-wired code; say so in Scope.
5. **Compile the known-items list from the findings ledger.** Each review directory keeps a machine-readable `findings.json` — a JSON array, one object per finding with keys `id` (`F1`), `severity` (`BLOCKER|HIGH|MEDIUM|LOW`), `origin`, `scope`, `title`, `location` (`file:line`), `status` (`open|fixed|partial|rejected|wontfix`), `fix_sha` (nullable); for `rejected` items a `premise` field is required — the specific code line or tooling semantics the rejection rests on, **quoted, not paraphrased**; `wontfix` items instead carry a `deferred_until`/`reason` field (a scope decision, not a head-re-checkable technical premise). Statuses are conclusions; premises are evidence — the ledger carries both, and every round re-checks each premise at its head: a premise that no longer holds reopens the finding. Generate the known-items list (prior findings + statuses at the reviewed head, previously verified-clean items, deliberate behaviour changes, aggregator-resolved facts) from the ledger — never re-derive it from prose reports. Verified-clean items and deliberate behaviours have no severity and are not findings; persist them in a sibling `known-clean.json` (one entry per item, with the quoted code) so they survive across rounds too. Hand it to sub-agents (full mode) or use it to skip re-derivation (delta mode). The ledger is also the cross-session record: a review continued in a later session resumes from it — when the head has advanced, locate the prior ledger by globbing `.agents/reviews/pr-<number>-*/findings.json` (newest non-empty first) — not from conversation context.
6. **Read the diff against the checklist** in [references/checklist.md](references/checklist.md). Delta mode: targeted greps from the main thread. Full mode: delegate per module under the contract below. Run the sanity checks and record non-findings under "Checked, and not a problem" — each with the quoted code that establishes safety (see Review shape item 5).
   - **A fix is not a re-review.** Confirming the mechanism a prior finding named (the shared helper now exists, the predicate was added) is not the same as re-running the checklist over the region the fix touched — a half-fix (one of two copies consolidated, one of two divergent behaviours aligned) passes the "named mechanism" check while leaving the second half intact. In delta mode, for every fixed/partial finding, re-apply the checklist items the original finding was classified under, over the full function/region the fix changed — not just the line the finding pointed at.
   - **Reachability probe.** Ask the question the fix never asked: who can reach the new code or branch, with what inputs, over which wire/method versions — answered from greps over the materialized tree, never from the fix commit's own message. (A fix whose commit message said "close findings" once added a version gate no honest payload could pass.) **Severity is set by the consumer of an asymmetry, not by the asymmetry itself.** When two lanes diverge (per-tx capacity fault tagged with a txHash, whole-block not), trace what the consumer does in *each* shape before grading: #5549's capacity/txHash drift was filed LOW on "the consumer checks `OpRejectIsCapacity` before evicting", but the skip path gates on `culprit.has_value()` *first*, so the hash-less shape fell through to `-32603` — the "safe" branch was dead code and the real severity was HIGH.
7. **Bound what you verified — target closure.** Enumerate every build/test target the diff touches and compile + run each one; a "suite green" claim must name the affected-target list, never a single default suite. A fix that lands a test in `bcos-rpc` while the loop only runs `test-bcos-engine` has verified nothing about that test — and a compile break in the un-run target is exactly how a BLOCKER walks past a green loop (e.g. a test cited in the description whose target was never built). Also state which files you could not read (e.g. modules outside the diff or outside the repo). A test that bypasses a layer (struct copy instead of the RPC JSON round trip) is itself a coverage finding even when you cannot prove a defect. **A finding whose disposition depends on a file you could not read may only be marked "could not determine", never "fixed"/"rejected"**: the #5549 Round-2 reviewer downgraded its delegate-serialization HIGH to a comment and carried it at MEDIUM precisely because `OpScheduler.h` was not in its materialized tree — closing on a rationale you could not verify is how a false premise survives the round.
8. **Aggregation gate (full mode).** Before a sub-agent finding enters the report, re-verify it at its `file:line` in the materialized tree and check the quoted evidence matches. Drop or downgrade anything unverifiable; treat "checked clean" claims as unverified unless they quote the code (see Review shape item 5).
   - **Unresolved sweep (both modes).** Before writing the report, sweep every "could not determine" left by agents or the main thread. The default action is to **resolve** it — one targeted grep/read, whenever the minimal read set lies inside the materialized tree; the interface closure from step 2 makes most cross-module questions in-tree-resolvable. Only facts genuinely outside the tree may be parked, explicitly in the verification boundary, with the minimal read set and why it cannot be resolved in-session. None may silently vanish, and nothing tree-resolvable may be parked.
9. **Write the review in the repo's format** (below). If the author replies, respond per-finding: `Fixed in <sha> — …` / `Not changed — …` (one sentence inline, evidence in the round summary reply) or a justification, not silence.

## Finding format

One block per finding, in severity order:

```
### [Fn] <short title>
**Severity:** BLOCKER | HIGH | MEDIUM | LOW
**Origin:** INTRODUCED (this PR) | PRE-EXISTING (already on base)
**Scope:** live production path | new API, no production caller yet (incl. shared infra consumed by later stack PRs) | build graph | tests
**Location:** <file>:<line>   (of the materialized head tree)
**Evidence:** ≤6-line verbatim code quote from that location
**Problem:** what the code does vs the base or the description's claim.
**Why it matters:** reachable impact with a concrete scenario (who calls it, retry /
  concurrency / wire-dialect / config details that make it fire).
**Recommended fix:** actionable; prefer consolidating shared code over patching symptoms.
```

No finding without evidence. If a suspected issue needs proof you cannot obtain, say so explicitly in the finding ("could not determine X") instead of asserting a clean negative.

Severity semantics used in this repo's history:

- **BLOCKER** — live-path correctness with a reachable scenario and chain-wide or
  re-execution consequences (double commit of one block, use of a moved-from object,
  second ledger prewrite); or a repo-wide build/CI gate that fails **deterministically**
  for the whole test target and outlives this PR (an unvendored-but-required fixture
  behind a CI-forced macro — every future PR touching the target inherits the red).
- **HIGH** — live-path defect with narrower trigger, or an **undisclosed behaviour
  change** with a terminal consequence (e.g. `SYNCING` with no sync mechanism), or a
  capability/version mismatch that strands a client.
- **MEDIUM** — wrong or drift-prone in code that is new/not yet wired but will be
  consumed by the next PRs in the stack; duplicate implementations of one job;
  predicate asymmetries; lock held across `co_await`.
- **LOW** — build-graph hygiene, dead/duplicate code bounded by a later deletion,
  comments naming things that don't exist, pure formatting churn.

## Review shape (in order)

1. **Summary** — what the PR really is: the description's classification vs the diff (e.g. "file split, but also rewrites the semantics of the live X path").
2. **Findings**, ranked by severity.
3. **Scorecard** — `| Dimension | Score /10 | Reason |` using this repo's dimensions: Correctness, Tests, Comments/readability, Scope discipline, Description honesty; plus an overall `N / 10` and a disposition (`APPROVE`, `CHANGES_REQUESTED`, `COMMENT` — pick one).
4. **What this PR is doing** — old→new mapping; which moves are byte-equivalent (pinned by gold tests) and which are *intentional changes* that must appear in the description.
5. **Checked, and not a problem** — each with the quoted code that establishes safety (the same evidence standard as a finding): overflow-safe arithmetic forms, unreachable defensive branches, lock ordering, dead comparison arms.
6. **Verification boundary** — what was and wasn't built, executed, or readable.

**Converged-round fast path.** Three preconditions gate the fast path — a round claiming convergence without them reopens: **(a) zero unaudited surface** — every commit absorbed into the ledger (parallel-session or head-drift) has been diff-read and its affected targets verified; **(b) the approval round is a full round** — the round that concludes APPROVE runs a full-surface re-hunt at the terminal head (delta mode only ever sampled the delta plus its neighbourhood; the terminal head has never been hunted whole); **(c) every disclosed behaviour change verified to match the code** (a disclosure whose text contradicts the behaviour is **mis-disclosed** and blocks convergence). When the preconditions hold and a round closes with every prior finding fixed or rejected-with-verified-premise at an unchanged (or trivially-changed) head and no new findings, the report collapses to: prior-status table + convergence statement + scorecard delta; sections 4–6 shrink to one line each. Reports are written in the repo's review language (English, matching the recorded review history); the start/finish lifecycle markers stay in Chinese (user-facing chrome), so the two are intentionally split.

Stamp the report footer with `Reviewed with fisco-review v<version>` (the frontmatter `version:`) so the checklist version that produced the findings is recoverable, plus the round's measured cost when sub-agents ran (`subagents: ~N M tokens / M agents`) so cost-vs-recall is traceable across rounds, release the review lock (`scripts/lock.sh release <dir>`), then print the finish marker `review PR #<number> 结束` as the final line.

**Rounds:** label each review "Round N at head <sha>". Open by re-checking prior findings ("7 of 9 fixed at <sha>; F2 remains open because …"). State the convergence rule and a round ceiling. **Convergence** = every prior finding fixed or rejected-with-verified-premise at an unchanged head, no new findings, and every disclosed behaviour change verified against the code (details in the converged-round fast path below). **Round ceiling** = the maximum number of rounds before you stop iterating and call it done or request a different resolution (e.g. 2–3). A new HIGH or BLOCKER in a round resets convergence, as does an **undisclosed or mis-disclosed behaviour change** (a disclosure whose text contradicts the code).

## Delegation (full mode)

See "Deep-mode delegation contract" in [references/checklist.md](references/checklist.md) for budgets and rules. Core: one module per agent, files read at most once, **hard cap ~2M tokens / ~35 tool calls** (exceeding it stops the agent and the main thread takes over its un-covered files — see the checklist), evidence quotes required, no exhaustive negative-space claims, known-items list passed in so agents report only NEW findings. Each agent also runs the cross-cutting tasks — claim-audit (item 1) and the conventions axis — per the contract, and the aggregator must not inject candidate answers into prompts. The aggregator pre-resolves build/CI/config artifacts (workflow files, CMakeLists, provision scripts) on the main thread and ships the results inside the known-items list — agents never re-read them. Cross-file symmetry (sibling-helper step-set parity, duplicated consensus literals) is the **aggregator's** post-pass, not the agents' — it is a single continuous read that file-slicing cannot reproduce.

## Maintenance

When you edit this skill, bump the frontmatter `version:` per the semver policy in [CHANGELOG.md](CHANGELOG.md) and add a dated entry there. The version is stamped into every review report footer, so a stale version mislabels future findings. **A new checklist item must name the golden-set entry (or a concrete finding) it catches** — see [references/golden-set.md](references/golden-set.md); a rule added without a retrievable example is how the checklist grew 32→39 items without a measured recall gain.
